# DTS 产品能力与月度交付规划（2026-09-27）

**状态**：规划修订；业务口径和实施 ADR 仍由对应 Task 确认，非运行验收结论。排期按依赖关系编排，不按人力容量打折（用户 2026-09-27）。
**需求来源**：用户要求把“数据平台如何面向业务与 AI 演进”的讨论落实到 DTS 产品及 v1.0.0 Sprint。
**适用范围**：当前 [Sprint-5](../../sprint-5-202610/README.md) 与 [backlog](../../backlog/README.md)；不恢复 3 月未执行的 Sprint，11 月目录在 11-02 创建。

## 0. 一页结论

- **定位**：DTS 交付的是“业务人员能得到可信、授权、可追溯的数据与知识答案”，dts-stack 是支撑这一结果的可信数据底座，而不是先建后用的“中台”。
- **方法**：按场景交付。10 月写清 PRS“在营项目”场景、口径 oracle 与测量方法；11 月一个 Sprint 连贯完成：第 3 周打通第一条受控链（登录 → Pack 指标 → 受控查询 → 一致结果 → 审计），第 4 周全量验收与发布。v1.0.0 共两个月度 Sprint，不为单个 Feature 另开 Sprint。
- **能力**：C01 可信经营数据、C02 授权知识供给、C03 可复用行业能力、C04 可评估与人工接管，跨 Sprint 保留标识。
- **不做**：训练/标注平台、多模态流水线、新向量库或新服务；RAG 先探索（BL-A/T22）后决定。
- **风险**：业务口径与验收人未确认（§6）；stack 权威仓库未定（F0/T01）。

## 1. 产品判断与现状依据

DTS 为行业业务人员提供可信数据查询、知识获取和可追溯的决策辅助。数据接入、治理、指标、查询和 BI 持续服务业务 App，也作为 AI 使用企业数据的基础；用实际业务结果验证共用能力的价值。

本次讨论采用“按场景交付、明确数据责任、缩短反馈周期”的方向。对外表述随之调整：不以“数据中台”命名或售卖 dts-stack；行业 AppPack 由领域方拥有语义与资产、平台提供运行时、五条铁律作为统一治理，这与 Data Mesh 的领域所有、自助平台、联邦治理一致，可用于回应“中台已过时”的质疑。“中台消亡”“90% 人才转向 AI”“模型训练是唯一出路”等说法不作为 DTS 路线依据。v1.0.0 不新增通用训练平台、标注平台、世界模型或多模态流水线，不因文章增加向量数据库或新服务。

## 3. 模块分工与最小数据契约

**交付方法（ADR-013，用户 2026-09-27 确定）**：① 用 antd 6 自建、借鉴 shadcn-admin 模式的 DTS Console 外壳，以 mock 数据先做出全部功能点的界面（Sprint-5 F6）；② 界面评审后冻结 OpenAPI 契约，由 Console BFF 实现，BFF 只承担与前端的交互（聚合、裁剪、校验、错误映射、身份透传）（BL-C）；③ Pack 运行时、受控出口、审计、指标等领域模块按常规设计，提供完整 API 与测试，独立于界面可用。原型接真实数据、上线之前，其依赖的领域 API 与测试必须完成（铁律 #5 的解释）。

| 模块 | 本轮责任 | 约束 |
|---|---|---|
| dts-stack | 复用现有资产目录、指标发布、质量与查询能力，向业务页面、BI 和 studio 提供受治理的数据 | 指标 SoT 待 ADR-007 接受；不为 AI 另造指标库、资产标识或质量系统 |
| dts-studio | 消费指标与授权知识，组织问答、证据和评估；加载行业 Pack | 不成为业务事实源；不通过独立直连、服务账号兜底扩大用户可见范围 |
| dts-app-stack / PRS | 保有业务交易事实及规则；提供经确认的领域资产、业务样例和原业务操作路径 | 行业负责人确认口径；3 月原型仅作参考，9 月锁定 BOM 按已有承接记录验证 |
| DTS Console（`dts-studio/console/`） | 全部功能点的统一界面；PRS/stack 页面经模块联邦或链接挂入 | 只经 BFF 访问后端；不自行判断权限；不重写存量 antd 页面 |
| Console BFF（`dts-studio/console-bff/`） | 按冻结契约聚合下游、透传用户身份、统一错误体 | 无业务规则、无业务数据库、无服务账号提权；不绕过 dts-gateway |
| dts-wiki | 保有文档原文、版本和空间权限，提供受控内容接口 | 向量索引若后续采用，只是派生检索数据；PG 内容和权限仍是权威来源 |
| dts-infra / RDC | 运维方案、发布证据与跨模块规划 | 沿用 Compose 验证范围，不增加 k8s/Go infra 实现承诺 |

“数据产品”在此指已有数据能力的可消费交付单元，不要求新建产品中心页面。C01 在现有目录、指标/API 与 Pack 上补齐以下信息，字段名及复用映射由 F0/T14、BL-D/T17 定稿：

- 身份：复用资产标识、指标引用与版本；业务负责人和技术维护责任。
- 语义：在营规则、明细粒度、统计时点、过滤条件、来源关系；未确认项不能发布为正式口径。
- 信任：数据快照/更新时间、质量检查结果、适用的数据新鲜度要求。
- 消费：现有页面/API、AI 对同一指标的引用；来源、版本与 traceId 能关联，不改造出第二套答案消息协议。
- 访问：真实用户、租户、角色和用途由可信身份链传入；业务标签不能充当安全分类或权限。

C01 的发布资格和查询权限分别判断。未发布/已撤回的指标、401/403、租户缺失不得使用缓存兜底；服务短暂不可用只允许在授权仍有效、已发布版本和明确有效期内降级，并显示原因。缓存不能把缺权限伪装成“没有数据”。

C02 的读取链为“用户/Agent → Wiki 授权接口 → 空间权限校验 → 原文与版本”。Wiki 的空间角色不能直接等同 PRS 租户；跨 realm 的代用户授权由 BL-A/T22 探索。10 月不借用 SQL QueryGateway 承载文档，也不假定机器身份接入已实现。

## 5. 价值、质量与证据

| 指标 | 定义与判定 | 责任 Task |
|---|---|---|
| 正确性与一致性 | 同用户/租户/快照/口径版本下，对照独立确认的项目集合与计数；错误计数零容差 | F0/T04、BL-D/T17、BL-E/T01 |
| 授权与来源 | 跨租户/空间泄漏为 0；每个成功结果可关联来源、版本和调用主体；不可用或拒绝均显式记录 | F3/T15、BL-S、BL-E/T01 |
| 数据新鲜度与质量 | 记录更新时间、检查结果和过期处理；具体有效期由业务频率确认，缺少时不得标为已达标 | F0/T14、BL-D/T17 |
| 问数效果 | 复用 golden set，按领域/路由记录通过、拒绝、失败及证据覆盖；保留未通过样本 | F0/T02、BL-A/T10、BL-E/T01 |
| 使用价值 | 同批任务记录人工/API、AI 各自完成时间、成功率和人工纠正次数；小样本只证明该场景，不承诺收益倍数 | F0/T04、T18、BL-E/T01 |
| 成本与时延 | P50/P95 分开记录模板/模型路径；记录调用次数、token 和可获得的计费成本，未知单价标未测；每次成功任务成本保留失败重试成本 | F0/T18、BL-E/T01 |
| 知识接入增益 | T22 使用固定问答集对照现有关键词检索，比较命中、引用版本、授权负例、时延/成本；无明确收益允许暂缓 RAG | BL-A/T22 |
| 可恢复 | AI 停止后，PRS 原业务路径与 stack 既有功能仍可用；发布前实际回退演练 | BL-E/T01、T02 |

没有当前业务测量数据，因此本轮不填写收益百分比、不预填测试 PASS。F0/T18 在 10 月完成预算、方法和当前基线入口，后续实现的 CI 接入与运行达标由 BL-E/T01 承接，避免 10 月 Task 依赖 12 月验收。
