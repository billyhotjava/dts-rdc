# T01: ADR-005 头脑实现语言与运行形态

**优先级**: P0
**状态**: DRAFT
**依赖**: F0/T01

## 目标
定稿"AI 头脑用什么语言、以什么进程形态运行"，解决 studio 设计（Python + LangGraph 10 服务，账本#29）与现实（copilot 是 Java 单体，账本#10）的冲突。

## 技术设计
- **备选方案**：
  - A：Java 主体（沿用 copilot），按模块拆成 `engine-ai`（智能体/NL2SQL/RAG/Pack 运行时）+ 可选 Python sidecar（eval、embedding、将来的多模态）；
  - B：Python 重写 AI Core（LangGraph），Java 只保留 BI/平台；
  - C：双栈并行，新能力用 Python、存量用 Java。
- **评估维度（必须逐项打分）**：存量资产复用（34 sprint、146 测试）、团队技能、铁律 #1 可降级性、LLM 生态成熟度（工具调用、流式、结构化输出）、部署复杂度（离线交付的镜像数）、迁移风险与工期、与 stack（Java）的集成成本。
- **推荐**：A。理由：Spring AI / LangChain4j 已能覆盖工具调用和流式；Python 的优势（评测、embedding、数据科学）通过 sidecar 获得；B 至少 3–4 个月且会冻结产品迭代。
- **ADR 必须写明**：
  1. 头脑进程清单：`dts-studio-engine-ai`（原 copilot-ai）、（BI 若按 ADR-006 归 stack，则 copilot-analytics 不进入头脑）、`dts-studio-webapp`（原 copilot-webapp）；
  2. sidecar 协议：HTTP/JSON（与 LLM Gateway 一致），不引入 gRPC；
  3. 可降级约定：头脑整体下线时，prs 与 stack 的所有功能不受影响（铁律 #1），并列出需要验证的依赖点；
  4. 回滚条件：如果 Java 生态在 2 个季度内无法支撑某项关键能力（列举），重新评估方案 C。
- **产出**：`docs/adr/ADR-005-brain-language.md`。
