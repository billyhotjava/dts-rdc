## 1. 决策汇总

| # | 决策 | 结论 | 理由要点 |
|---|------|------|----------|
| D1 | 租户语义（Q1） | **租户 = 企业内的子公司/业务单元**；一套部署服务一个企业（私有云为主）；部门只做租户内权限 | 私有云单企业交付；公有云按“一企业一套部署” |

## 2. 模块地图与依赖规则

```
 用户界面   门户/管理台(base)  Wiki  数据平台(stack)  BI(analytics)  AI工作台(studio)  行业App
                │               │        │               │               │              │
 业务能力层      │            dts-wiki  dts-stack ◄── dts-analytics ◄── dts-studio ──► dts-app-stack
                ▼               ▼        ▼               ▼               ▼              ▼
 公共底座   dts-base：门户 · 租户/组织/用户管理(写回 Keycloak) · forwardAuth(base-auth) · 审计中心 · 汇总授权
                ▼
 基础设施   dts-infra：K8s · Harbor · CI · Keycloak · PostgreSQL · Kafka · S3 · Traefik · cert-manager · 可观测 · dtsctl
 契约       dts-common：跨模块 schema/规范/离线工具；任何模块可选依赖，自身无依赖
```

1. 依赖单向无环：上层调下层或同层右侧；下层不回调上层。现 analytics → studio 数据源 API 的反向依赖随 D3 消失。
2. 跨模块只走带用户身份的 API（HTTP/SSE/MCP）；不共享数据库、不引用对方源码；AI 代调用统一 Token Exchange。
3. `base-console` 停机只影响管理界面：登录依赖 Keycloak 与无状态 `base-auth`；审计事件在 Kafka 暂存，恢复后补落库。
4. studio 停机其余模块照常可用，AI 嵌入组件降级隐藏。
5. infra 只负责部署与运维，运行时无业务服务依赖 dtsctl/operator。

## 3. 模块职责边界

| 模块 | 负责 | 不负责 | 本期处置 |
|---|---|---|---|
| dts-infra | K8s（研发 RKE2；交付品牌化 RKE2/ACK）、Harbor、CI、中间件 chart、chart/契约规范、dtsctl、可选 Rancher | 业务逻辑、身份数据 | **第一阶段**：研发运行底座 |
| dts-base（新仓库） | 门户与统一导航、租户/部门/用户/角色管理（Admin API 写回 Keycloak）、`base-auth`（forwardAuth）、审计中心（Kafka → append-only + 哈希链 + 查询）、集团汇总授权登记 | 人员主数据、业务工作流、dts-admin 定制功能 | **第一阶段** |
| dts-wiki | 原文、版本、空间权限、评论、检索、结构化查询（sprint 看板）、MCP/llms.txt、git 同步 | 向量索引权威性 | **第一阶段，最先上线** |
| dts-stack | 接入、目录/元数据、建模、治理/质量、指标唯一事实源、数据源注册与凭据、QueryGateway（含租户过滤与汇总通道） | BI 呈现、AI 编排、身份/审计（迁出到 base） | 延后；多租户重构单独设计 |

| dts-studio | D8 八层、AI 工作台、AI 嵌入组件 | 数据、指标、文档、身份、审计存储、业务交易 | 延后；删除 JDBC 直连，领域硬编码迁 Pack/App |
| dts-app-stack | 行业交易、领域资产（Pack 来源）、供 AI 调用的动作 API | 平台能力 | 暂缓，只保持可构建 |
| dts-common | Pack schema/CLI、审计事件 schema、身份 claims/租户上下文规范、错误体、QueryGateway 与 AI 嵌入消息 schema | 运行时代码、框架、数据库 | 第一阶段补 K1/K3/K5 规范 |

## 4. 第一阶段契约

| # | 契约 | 要点 | 落位 |
|---|---|---|---|
| K1 | 身份与令牌 | 产品 Keycloak 两个 realm：`dts-ops`（集群/运维/可选 Rancher）与 `dts`（业务）；`dts` 中 Organization=租户、Organization 下 Group=部门、realm/client 角色=权限；服务端应用用 confidential + 授权码，SPA 用 PKCE；token 只带**一个当前租户**（登录选择，`organization:<alias>` scope），切换租户即重签；代调用带 `act` | dts-common `identity-claims` 规范；infra realm 代码 |
| K2 | 网关鉴权 | Traefik（Gateway API `HTTPRoute`，T02 已定）→ forwardAuth → `base-auth`（无状态、多副本、只依赖 JWKS）：验 token、查应用访问权、注入 `X-DTS-User/Tenant/Roles/Trace-Id`；服务仍自行验 JWT（纵深防御） | dts-base、infra chart-spec |
| K3 | 审计事件 | CloudEvents 1.0，Kafka `dts.audit.v1`；服务经 outbox 投递；Keycloak 登录/管理事件经事件监听扩展接入；apiserver 审计由 infra 接入；base 消费落 append-only 表 + 哈希链；`actor` 与 `act` 双主体 | dts-common schema；base |
| K4 | 应用注册与导航 | 各模块 chart values 声明应用名称、URL、图标、所需角色，部署时登记到 base；门户按角色过滤；统一导航栏为 JS 组件包 | base；chart-spec 增补 |
| K5 | 错误体 | RFC 9457 `application/problem+json` + `errorKey`、`traceId`、租户/权限标准码 | dts-common |
| K6 | Wiki Agent 接口 | REST 查询 + MCP Server；MCP 用 OAuth 2.1 对接 Keycloak；Agent 以个人身份（设备授权）接入，空间权限照常生效，不用共享服务账号 | dts-wiki（F3/T15–T16） |
| K7 | Chart 与连接契约 | 沿用 dts-infra `docs/chart-spec.md`、`docs/contract-spec.md`；base、wiki 为首批 | dts-infra |

### 5.2 身份两层（D13）

| 层 | 实例 | 使用者 | 管理方式 |
|---|---|---|---|
| 公司 SSO | `sso.yuzhicloud.com`（E1，Compose），realm `yuzhicloud` | Jira、研发 wiki、公司办公、E2 上的研发工具 | 维持现状，dts-infra `deploy/sso` |
| 产品 Keycloak | E3 内，`https://sso.dts.yuzhicloud.com`，Keycloak Operator，DB 在 CNPG | realm `dts-ops`：Rancher（可选组件）、kubectl（apiserver OIDC + kubelogin）、运维控制台；realm `dts`：dts-base、产品形态 wiki、后续业务模块 | realm/client/role 全部由 keycloak-config-cli 代码化（F7/T19），可整体重建 |

- **Rancher（2026-10-04 完成）**：E3 上的 Rancher 2.15.2 曾于 10-03 接入公司 SSO；按 D14（E3 不用公司账号），10-04 以 `rancher-cleanup` 清理后在 `https://rancher.dts.yuzhicloud.com` 重装，唯一外部身份为 `dts-ops`（ops-admins/developers/viewers），本地 admin 仅作应急通道（证据 `it/infra/S1-identity.md`）。Rancher 仍以 helm 手工安装，chart-spec 化与 dtsctl 可选组件化另立 F7 Task。
- **应急通道**（铁律 1，客户现场同样适用）：RKE2 证书 kubeconfig 只留在节点本地；Rancher 本地 admin、产品 Keycloak `master` 管理员均封存，一经使用即记审计。apiserver 开启 OIDC 后证书认证仍然有效，Keycloak 故障不会阻断 apiserver 启动。每次身份变更后都要实测应急通道。
- **安装顺序**（即 dtsctl 的步骤）：RKE2（证书认证）→ CNPG + PG → Keycloak Operator + 实例 → config-cli 导入 realm → 开启 apiserver OIDC（结构化认证配置）与可选的 Rancher OIDC → 封存应急凭据。
- **wiki 双形态**：研发 wiki 运行在 E1、接公司 SSO；产品形态 wiki 运行在 E3、接产品 Keycloak `dts`。OIDC 参数全部来自 oidc 连接契约，不写死 realm。
- **公网入口**：E3 的产品域名（`*.dts.yuzhicloud.com`）都沿用阿里云 Nginx 边缘 + WireGuard → 节点 Traefik 的链路；每个域名需要单独的边缘 vhost 和证书（`sso.dts` 的 DNS 已于 10-03 生效，vhost 和证书尚未配置）。

## 10. 风险与验证

- 单 PVE 物理机承载三节点：节点冗余不防物理机故障；产品 Keycloak 与 PG 需 CNPG 备份到 S3（S2 落地前先做本地快照）。若 E2 也在同一宿主，构建负载会与 E3 争用资源。
- 循环依赖：每次变更后实测应急通道可用。
- 验证证据入 `it/infra/`、`it/wiki/`：OIDC 登录（两个 realm）、config-cli 重复 apply 无差异、apiserver OIDC + kubelogin、base-auth 拒绝无效 token、审计事件端到端可查。
