## 用户与授权来源

工程已存在 `jhi_user`，由 OAuth 登录同步（`UserService.syncUserWithIdP`）；`skipUserManagement` 关闭本地密码管理，不表示没有用户表。不新建 app_user。本期候选限已登录同步的本地用户，未出现的同事先完成一次 Wiki 登录。

`GET /api/wiki/users/mention?q=&spaceSlug=` 先验证调用者可读空间，再从本地用户检索候选，并校验候选的当前有效身份/空间读权限。登录时的 jhi_user_authority 只是快照，不能单独证明另一用户现在仍有权。当前权限查询复用 F2/T09/T10 的同源判定；缺少按目标用户查询能力时，本 Task 增补服务端 Keycloak 权限查询适配器及最小只读权限，不能用管理员业务身份读取页面或让前端调用管理 API。

q 去首尾空白后 1～100 字符，空查询返回空候选；最多 20 条，响应仅 `{items:[{id,login,displayName}]}`，不带邮件或其他空间信息。有效权限判定包含读者/空间角色、组继承与管理员规则，和 SpaceAccessService 一致；身份服务不可用时返回明确不可用状态，不用过期名单兜底。

## 提及、关注和通知

- 编辑器/评论中插入可读的 `@login`，内容正常随 git 保存；候选选择的主体由服务端再次解析/校验，不信任客户端传入的角色。代码块与电子邮件中的 @ 不触发通知，重复提及只通知一次。
- 复用 JDL PageWatch 与 Notification；页面作者、编辑者、评论者默认关注。用户显式取消后持久化 `muted=true`（新的增量列），普通保存/评论不得重新自动开启；显式关注才清除 muted。
- 当前关注者/被提及者可通知资格与页面权限分别判断；被提及但主动取消关注仍可收到针对自己的提及通知，常规页面更新不通知 muted 用户。
- 页面/评论保存事务只记录通知意图，不在数据库事务中请求 IdP 或发邮件。处理通知意图、返回站内通知、打开通知链接及发送邮件时均校验收件者当前权限；撤权/禁用/删页后不显示标题、摘要或未读计数。权限查询失败则待重试，不提前发送。
- 邮件依赖 T06，可关闭；站内通知功能与当前授权校验仍须完成。重试按事件/收件人幂等，避免重复通知。

## 验证与完成标准

- [ ] 不存在 app_user 依赖；仅复用 jhi_user，并有候选查询/限额/不可用状态测试。
- [ ] caller 跨空间、目标用户撤权/禁用/组继承变化、伪造主体、发送前撤权、通知未读计数均不泄漏。
- [ ] 取消后再次编辑不自动关注；手动重新关注生效；重复处理只产生一次通知。
- [ ] 编辑器及评论 @候选、关注/取消、站内通知真实走查，证据入 `it/wiki/IT-04-pages.md`，F5/T10-A 验收。

## 通知意图增量字段与状态

复用 Notification，追加 `event_key varchar(200)`、`auth_state varchar(16)`（`PENDING`/`ALLOWED`/`SUPPRESSED`）及唯一 `(event_key,recipient_id,type)`。event_key 从同一页面版本/评论事件的稳定 ID 生成，重试不重新生成；旧行先以 `legacy:<notification-id>` 回填并设 PENDING，再建立非空与唯一约束。PageWatch.muted 默认 false，兼容已有关注。

PENDING 在异步校验成功后转 ALLOWED；确定失权/禁用/删页转 SUPPRESSED；权限源超时仍为 PENDING 退避重试。ALLOWED 只表示曾通过，不豁免列表/计数/发送时的当前授权校验。任何状态都不修改页面保存成功的结果；站内通知的 read_at 与邮件投递状态独立记录。新增状态/JDL 和迁移由本任务实现并测试，本轮只定义约束。
