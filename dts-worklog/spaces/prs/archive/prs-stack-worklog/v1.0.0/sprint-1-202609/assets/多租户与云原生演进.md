# 多租户与云原生演进（架构说明 v0.1）

版本：v0.1（2026-09-17，架构评审输入）。状态：提议，对应决策 R-010（多租户分级模型）、R-011（k8s-ready 约束与演进路线）。
用途：F2 规范（BOM/数据/部署章节）、F3 租户模型、F6 同步选型、F7 隔离验证的设计依据。
原则：现在写进规范的成本几乎为零，业务表建成后再补的代价很高。所以本期只做"约束 + 验证"，不做平台建设。

## 2. 多租户（R-010）

### 2.1 现状证据
- 老系统用 MyBatis-Plus `TenantLineInnerInterceptor`，但 `RsTenantHandler.ignoreTable`
  在**取不到租户时不加过滤、返回全部数据**，且只对配置白名单内的表生效
  （`adminapi/rs-common/rs-common-data/src/main/java/com/rs/common/data/tenant/RsTenantHandler.java:54-62`）。
- 手写 SQL 全靠拦截器解析，`rs-flowers-base` 的 mapper XML 中 `tenant_id` 出现 0 次。
- 租户 ID 为 `Long`（`TenantContextHolder`）；ODS 表均带 `tenant_id` 列。
- dts-platform 没有租户或场景隔离；多场景的既定方案是每个场景单独部署。
- 结论：现状是"带 tenant_id 列的单租户系统"，隔离在应用层，且默认放行。

### 2.2 分级模型

| 级别 | 形态 | 适用 | 数据面 |
|---|---|---|---|
| 标准（Pool） | 共享库、共享服务 | 大多数中小客户 | `tenant_id` + PG 行级安全（RLS） |
| 专享（Silo） | 独立库或独立 cell，代码相同 | 大客户、有合规要求的客户 | 独立 PG 集群 |
| 私有化 | 整套部署在客户侧，同一套 Helm chart | 机密级客户 | 独立全栈 |

不采用每租户一个 schema：迁移要跑 N 遍，连接池碎片化，运维复杂度最高。
租户目录（tenant → 级别 / cell / 数据库连接）是路由的唯一依据。

### 2.3 六个层面的约束

1. **身份**：一个 realm（`flower`），每个租户对应一个 Keycloak Organization；令牌中的组织声明由网关映射为
   `X-DTS-Tenant-Id`。不采用每租户一个 realm（租户多了以后 Keycloak 本身扛不住）。
2. **数据**：
   - 每张业务表 `tenant_id bigint NOT NULL`；唯一约束和业务索引以 `tenant_id` 打头。
   - PG 行级安全强制隔离：`ENABLE` + `FORCE ROW LEVEL SECURITY`，策略
     `USING (tenant_id = current_setting('app.tenant_id', true)::bigint)`，写入加 `WITH CHECK`。
   - 应用每个事务开始时执行 `SET LOCAL app.tenant_id = ?`（与 PgBouncer 事务模式兼容）；
     应用账号不是表的所有者，也不带 `BYPASSRLS`；取不到租户时返回 0 行（fail-closed）。
   - 平台级表（字典默认值、租户目录）单独归入 `platform` schema，不启用 RLS，仅限平台管理员账号写入。
   - 应用层租户过滤保留，作为第二道防线，不是唯一防线。
   - 单号：计数表 `(tenant_id, doc_type, period)` 行锁取号，不用全局序列。
   - 主键：雪花 bigint 全局唯一，租户迁出到独立库时无需改主键（与 R-008 规则 4 一致）。
   - 规模化：大表按 `tenant_id` 哈希分区；更大规模评估 Citus（以 `tenant_id` 为分布键，与 RLS 能否配合需验证）；
     超大租户迁到专享级别。
3. **配置与规则**：SpEL 结算规则、打印模板、字典、Flowable 流程（原生 `tenantId`）、功能开关，
   都采用"平台默认 + 租户覆盖"两层。
4. **运行时**：缓存键、对象键前缀、Kafka 消息头（`tenant-id`）、日志与链路属性都带租户；
   监控指标不以租户作为标签（除非租户数量可控）；定时任务按租户循环执行；Traefik 按租户限流。
5. **数据中台与大脑**：ODS/dbt 保留 `tenant_id`。copilot 生成的 SQL 不能靠提示词补租户条件，
   必须在执行层强制（Trino/Ranger 行过滤，或每租户独立视图和凭据）。
   dts-stack 目前"每场景单独部署"的方案只适合专享和私有化；标准级需要 stack 补行级租户策略（B-007）。
6. **控制面**（Sprint-2+）：租户开通流水线（建 Organization → 初始化种子数据 → 设配额 → 登记租户目录 → 通知 stack/copilot）、
   计量计费、租户迁出与注销（导出、删除、留存期）。

### 2.4 本期落地（Sprint-1）

- F2/T03 验证 RLS 在模板服务中真正生效（无租户返回 0 行、跨租户写入被拒）。

## 3. 云原生 k8s 演进（R-011）

### 3.1 判断
团队需要同时适应 PG 与 Keycloak，本期不引入 k8s 运行时。
dts-stack 目前全部为 compose（仓库中没有 Helm/Kustomize 文件），prs 不等 stack 迁移，只通过稳定的端点对接。

### 3.2 阶段

| 阶段 | 形态 | 内容 |
|---|---|---|
| 0（Sprint-1 起） | 用 compose 运行，代码按 k8s 要求写 | 见 3.3 清单；prs 同时维护一份 Helm chart（`helm lint`/`helm template` 通过即可，不要求集群） |
| 1 单集群 | k8s | Traefik 走 Gateway API；CloudNativePG（高可用、S3 备份、时间点恢复，补上 F4 推迟的 HA）；Keycloak Operator；External Secrets + OpenBao/Vault（对应 B-006）；cert-manager；Argo CD；Prometheus/Grafana/Loki/Tempo |
| 2 租户上规模 | 按级别部署 | 标准级共享部署，HPA/KEDA 自动扩缩（消费者按 Kafka 积压扩）；专享级独立命名空间和独立 CNPG 集群；Kyverno、NetworkPolicy、ResourceQuota |
| 3 多 cell / 私有化 | 一个 cell = 一整套 prs + PG | 租户目录负责路由；私有化用同一 chart 加离线镜像包，小规模环境用 k3s/RKE2；此时再评估服务网格（mTLS 取代 `X-DTS-Service`） |

### 3.3 k8s-ready 清单（阶段 0 必须满足，F2 部署规范引用，F4/T03 自检）
- [ ] 配置全部来自环境变量或挂载文件，镜像内不含环境差异和密钥
- [ ] 服务无状态：不写本地盘（文件走 S3 API），会话不存本机内存
- [ ] Actuator `liveness`/`readiness` 探针分离；`readiness` 包含数据库检查，`liveness` 不包含
- [ ] 优雅停机（`server.shutdown=graceful`），停机时长小于 k8s 终止宽限期
- [ ] 日志以结构化格式（JSON）输出到 stdout；接入 OTel Java agent
- [ ] 用 Jib 或 Buildpacks 构建镜像，以非 root 用户运行，镜像 tag 固定
- [ ] 定时任务支持多副本（ShedLock），并按租户循环执行
- [ ] 数据库迁移可重复执行、能加锁，不依赖只有一个实例在跑
- [ ] Helm chart 骨架：Deployment/Service/探针/资源限制/HTTPRoute（Gateway API）；`helm lint` 通过
