# F1: 迁移清单定稿与口径签字
产品 Feature：PF-TRANSFER；需求依据：四路核查报告（后端/口径/前端/财务，2026-09）+ 本 Sprint README。
负责人：待确认；优先级：最高（阻塞 Sprint-2 规划）；状态：IN_PROGRESS（T01 已组装 v0.1，待架构走读）。

## 使用场景与验收
调用者：Sprint-2 各域负责人、财务、架构。触发：Sprint-1 启动。
输入：四路核查原始报告；结果：`assets/迁移清单-v0.1.md` 定稿 + 口径确认表签字 + 首批域排序/财务单据目录确认 + 按业务能力组织的能力视图。
正常流程：T01 组装清单 → T02 财务逐条签核（§3+§4）→ T03 确认排序与单据目录 → T04 能力视图重组 → 清单 v1.0。
替代流程：财务对某口径纠正 → 回写清单并标修订记录，不改历史版本（另存 v0.2）。
失败流程：T03 到期未确认 → 按默认排序（现场作业→业务单据→项目摆位→供应链→财务）推进 Sprint-2 规划，待确认后调整。
规则与边界：清单只收执行项（能力/端点/状态/口径/修项），不收过程讨论；签字只针对 §3 口径与 §4 财务 23 问。
迁移按业务能力跟踪（R-004）：Sprint-2+ 各域认领的是能力，§1 handler 清单只作覆盖核对附表，不作为新 API 设计输入。
验收示例：Given 四路报告齐备 / When T01–T03 完成 / Then 清单 v1.0 发布且签字页齐全，Sprint-2 可直接分工。
本期范围：清单定稿 + 签字 + 排序/目录确认 + 能力视图。后续切片：各域按能力视图认领迁移（Sprint-2+）。非目标：技术规范（F2）、任何编码。

## 设计
概念与共享架构：清单即迁移期共享基线；维护责任：架构（端点/状态/技术项）+ 财务（口径）。
概要协作：核查报告 → T01 清单 → T02/T03 签核 → T04 能力视图 → v1.0 发布 → 各域认领；域划分同时作为 F6（数据共存）的输入。
关键契约：签字页格式（条目/结论/签字人/日期）；修订规则（只增修订记录，不改已签字条目）；
能力条目格式（能力 ID `CAP-<域>-<序号>`/名称/角色/触发/涉及状态机/关联 handler/关联口径/候选 MCP 工具名）。
UI 或使用路径：无（文档交付物）。
详细设计：见 T01–T03。
未决项：B-002（单据目录/排序）由 T03 关闭；B-001（负责人）待确认。
